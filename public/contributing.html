COMMUNITY CONTRIBUTION

Contributing to GuardAgent

Thank you for helping build open-source security infrastructure for autonomous AI agents. Here is how to set up your environment, write policies, run tests, and submit improvements.

Development Workflow

GuardAgent is written in modern Node.js with minimal external dependencies. We prioritize clean architecture, predictable evaluation logic, and zero runtime bloat.

1

Clone and Install Dependencies

Fork the repository, clone your fork locally, and install dependencies:

Terminal 
git clone <your-fork-url>
cd GuardAgent
npm install
2

Start the Local Gateway

Launch the Express server in local development mode:

Terminal 
npm start

By default, GuardAgent runs on http://localhost:3000 in zero-config memory mode. No database configuration is required for local testing.

3

Execute Automated Tests

Run the automated verification suite to validate all security rules, evaluation paths, and API endpoints:

Terminal 
npm test

All PRs must pass the test suite with 100% success rate before being considered for review.

Code Architecture & Repository Layout

Key directories to navigate when implementing enhancements or fixes:

Path Purpose
server/services/securityEngine.js The core 12-step evaluation pipeline: input validation, agent auth, policy checks, risk scoring, and tool mediation.
server/services/toolRegistry.js Registered tool definitions (SQL, HTTP, filesystem, financial) and mock execution dispatchers.
server/database/store.js In-memory data store with pre-seeded demo fixtures for zero-dependency local development.
server/routes/ Modular Express route handlers (requests.js, policies.js, approvals.js, audit.js, agents.js, health.js).
public/assets/css/main.css Unified design system tokens, layout grids, components, and responsive typography.
tests/test-api.js Integration test suite verifying gateway decisions, schema integrity, and audit tamper resistance.

How to Contribute New Security Policies

To add a domain-specific guardrail (e.g., Kubernetes API guardrails, cloud CLI safeguards), follow these conventions:

  1. Deterministic Identification: Identify the target tool name and action verb. Avoid vague regular expressions that can be bypassed by whitespace variations.
  2. Parameter Inspection: Extract parameters safely using optional chaining. Never execute unvalidated input in dynamic evaluation contexts (e.g., avoid eval()).
  3. Transparent Rationale: Provide a clear, human-readable rationale string explaining why the policy triggered and what threshold was breached.
  4. Assign Meaningful Severity: Mark immediate destructive actions (e.g., dropping data, privilege escalation) as CRITICAL or HIGH. Mark operational thresholds (e.g., transaction limits) as MEDIUM with REQUIRE_APPROVAL.
  5. Write an Integration Test: Add corresponding test assertions to tests/test-api.js validating both allowed and blocked variations of the pattern.
Pull Request Checklist: Ensure your PR includes: (1) descriptive title following conventional commits (feat:, fix:, docs:), (2) updated tests in tests/test-api.js, (3) documentation updates in public/docs/ if routes or parameters changed.

Responsible Vulnerability Disclosure

As a cybersecurity platform, the security of GuardAgent is paramount. If you discover a security vulnerability or bypass technique within the evaluation engine, please do NOT disclose it via a public GitHub issue.

Please report security vulnerabilities through our private security advisory channel or by contacting the maintainers securely. We will acknowledge receipt within 48 hours, coordinate a remediation timeline, and credit your discovery in our security advisories.
