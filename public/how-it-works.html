TECHNICAL ARCHITECTURE

The Request Lifecycle

A deterministic, step-by-step walkthrough of how GuardAgent intercepts, validates, evaluates, and controls autonomous AI agent actions.

9-Step End-to-End Pipeline

Each phase executes sequentially with zero reliance on non-deterministic LLM self-reflection.

01

Phase 1: Action Request Submission

An AI agent proposing a tool call transmits an HTTP POST payload to /api/requests/evaluate. The payload contains the agent's identifier, target tool, intended action name, and parameter map.

INCOMING JSON PAYLOAD REQUEST 
{
  "agent_id": "agt-customer-support-01",
  "tool_name": "db_read_query",
  "action_name": "fetch_order_records",
  "parameters": {
    "customer_id": "cust_9921",
    "limit": 10
  }
}
02

Phase 2: Perimeter Schema & Syntax Validation

The gateway checks that all required fields are present, correctly typed, and conform to the registered schema. Malformed payloads, missing identifiers, or unexpected nested structures immediately fail with an early BLOCK decision.

03

Phase 3: Agent Identity Authentication & RBAC Check

GuardAgent queries the internal agent registry. The agent must exist, maintain an ACTIVE status, and possess an authorized role allowing access to the specified tool_name.

Deny-by-Default: If an agent attempts to invoke a tool outside its registered permission list, the request is blocked immediately without evaluating parameters.

04

Phase 4: Declarative Policy AST Evaluation

Active security policies linked to the target tool are evaluated against the parameter payload. GuardAgent checks numerical ceilings (e.g. transfer limits, row count caps), prohibited CIDR ranges (e.g. cloud metadata 169.254.169.254), and regex pattern violations (e.g. SQL injection fragments, raw shell commands).

05

Phase 5: Explainable Risk Score Computation

The risk engine aggregates findings into a 0–100 score:

  • • Base Tool Criticality: Read queries (Low) vs. Administrative writes (High).
  • • Parameter Severity: High numerical amounts or sensitive flag overrides add risk points.
  • • Policy Warnings: Partial rule matches trigger elevated scrutiny.
06

Phase 6: Deterministic Security Decision

The decision engine selects exactly one outcome:

ALLOW Score < 70 and all rules satisfied.
REQUIRE APPROVAL Score 70–89 or approval flag active.
BLOCK Score ≥ 90 or direct policy violation.
07

Phase 7: Human Review Workflow (Conditional)

If the verdict is REQUIRE_APPROVAL, the gateway generates a unique approval_id and records the request in a pending queue. Execution halts. The agent receives a paused notice. If a human reviewer does not provide an authorized approval token before the TTL expires, the request automatically transitions to EXPIRED and tool execution is cancelled.

08

Phase 8: Controlled Tool Invocation

Upon an ALLOW verdict (or subsequent human approval), the controlled executor invokes the tool function within an isolated execution context using pre-configured system credentials. The agent itself never possesses the underlying database credentials or API keys.

09

Phase 9: Cryptographic Event Commit & Return

The complete transaction receipt (including correlation ID, timestamps, decision rationale, and tool execution status) is committed to the structured audit log. The final response is returned to the calling agent.

FINAL GATEWAY EVALUATION RESPONSE JSON OUTPUT 
{
  "success": true,
  "request_id": "req-13929-w0zs",
  "correlation_id": "corr-4zfto64w",
  "decision": "ALLOW",
  "risk": {
    "score": 15,
    "level": "LOW",
    "factors": []
  },
  "rationale": "Verified safe read operation within policy limits.",
  "triggered_policies": [],
  "execution": {
    "status": "COMPLETED",
    "result": { "rows_returned": 10 }
  },
  "timestamp": "2026-10-19T14:32:01.112Z"
}
